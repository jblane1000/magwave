# FR coverage against PRD section 9

This page records what the v0.1 acceptance gate can actually claim, requirement by requirement.
It exists because a green test suite is not the same as an evidenced requirement: three of the
fourteen FRs in the gate had no implementation at all until 2026-11-25, and the CLI's own help text
was the evidence.

Commit this describes: `5a347cc` on `main`.
Method: each requirement was read from `docs/PRD.md`, then matched to a named test or a command I
ran. Where nothing could be found, the row says so rather than citing something adjacent.

Column meanings:

- **Satisfied** means a test in CI exercises the acceptance criterion, or I ran the command and saw
  the criterion hold.
- **Unverified** means the behaviour may exist but nothing in CI proves it.
- **Not satisfied** means no implementation exists.

## 9.2 Benchmark thresholds

27 analytic cases are green (the gate asks for at least 12). Solenoid and cuboid residuals in
`docs/BENCHMARKS.md` are between 1e-12 and 1.4e-5 relative, far inside the 1 % requirement. The
two-magnet force case is gated through the delta-convergence work recorded in ADR 0009, where the
extrapolated value carries a stated uncertainty band rather than a single hand-picked step.

Status: Satisfied.

## 9.3 BENCHMARKS.md regenerated by CI and committed by the release workflow

`.github/workflows/release.yml` regenerates the table with `tools/render_benchmarks.py` and then
runs `git diff --exit-code docs/BENCHMARKS.md`, so a committed table that differs from a fresh render
fails the release build. The gate was proved by breaking it on purpose: run 45741827205 carried a
hand-edited benchmark number and failed on exactly that step, with the `windows` and `publish` jobs
skipped. The following run, 45742031877, was green after the revert.

Status: Satisfied.

## 9.4 Licence clean, no network at runtime

Licence: `tools/check_licence_boundary.py` runs in CI and reports no GPL linkage.

Network: `tests/test_offline_runtime.py` replaces `socket.socket`, `socket.create_connection` and
`socket.getaddrinfo` with a raising stub, then runs the `validate`, `run` and `solve` paths inside
that block. A second test proves the stub itself trips on all three calls, so the test cannot pass by
being inert. It runs in the CI `build` job on every push.

Status: Satisfied.

## 9.5 First-run walkthrough executed by a second person or fresh VM

Not done. The automated offscreen walkthrough behind FR-061 is not a substitute: it drives the widget
tree with knowledge of the case name and tolerances that a first-time user would not have.

Status: Not satisfied. Needs either a second person or a clean VM following the README.

## What stands between this page and a v0.1 tag

1. The 9.5 walkthrough. Either a second person or a clean VM follows the README from a fresh clone
   through import, assign, run and slice, without help from someone who knows the answers. This is a
   process step, not code.
2. A real version bump and tag. `pyproject.toml` still reads 0.0.1; tagging it `v0.1.0` is what
   makes the `publish` job create the release. The smoke tags used to test the workflow have been
   deleted, so no release exists on the repository today.

Everything else in section 9 is now evidenced by a test or a run.
